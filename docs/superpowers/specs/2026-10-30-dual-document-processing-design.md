# 双路线文档处理设计

状态：用户已于 2026-10-30 确认开始实施，并补充要求在设置中保留两条路线切换选项。

## 目标与已确认决定

在 `feat/document-processing` 分支保留现有处理路线，新增从读取文档、组织笔记、形成知识树层级到生成藤蔓关系均由内置大模型 API 完成的路线，重点改善大文件因本地解析而无法继续处理的问题。

用户已选择复用现有 API，允许本地把文档转成页面图片。程序可以进行文件校验、格式转换、分页渲染、分批调度、结构校验和持久化；文档内容识别、章节理解、笔记组织和关系判断由模型负责。用户也授权检索和借用合适的 GitHub 开源项目。

两条路线共用现有课程、Notebook、Asset、版本、来源、知识树和关系数据。旧资料和省略路线参数的旧客户端继续使用原路线。新路线失败时明确报告原因，不静默改走原路线，也不使用离线拼接代替模型生成。

## 现状与证据

- `services/uploads.py` 当前在接收阶段限制文件大小、PDF/PPTX 页数及 DOCX 段落与表格数量。当前本机配置是 50 MB 和 500 个位置。
- `workers/material_worker.py` / `asset_worker.py` 通过 `document_processing/service.py` 生成 Document IR；现有实现依赖 native / MinerU、本地 OCR 和可选局部视觉补充。
- `document_processing/engines/pdf_text.py` 先构造包含所有页面的 `RawDocument`；新路线不调用这一整份文字/版面提取流程。
- `generation/context.py` 要求当前成功的解析版本，且质量允许生成；`generation/planner.py` 通过本地规则确定章节、重复内容及批次。
- `workers/notebook_generation_worker.py` 分批生成正文，但批次结果暂存在内存，全部完成后写入；中途失败会重新进行先前的模型调用。
- 知识树读取由 Notebook 正文派生的小节索引；`forest/notebook_relations.py` 调用模型判断藤蔓关系，但候选在 `relation_candidates.py` 中先按标题词重合排序并各截取 24 个小节。
- 本机现有 API 配置为 DeepSeek 官方接口、`deepseek-flash`。官方文档已核实其支持图片输入，Files API 支持的是图片而非 PDF/PPTX/DOCX 原文件。
- 本机常见安装位置存在 Word 和 PowerPoint，未发现 LibreOffice 的命令或常见安装路径。应用存在不等于转换已验收，实施时必须用合成样例实际验证。

以上是静态调用链和配置检查，尚未复现某一份用户大文件的具体报错，不能据此宣称已定位所有大文件失败原因。

## 方案比较与开源复用

### A. 现有 API + 逐页视觉读取（用户已选）

本地转页后调用现有模型，模型识别结果继续写入 Document IR，复用现有来源、检索和正文存储契约。优点是沿用现有 API 和数据体系，可独立检查每页并恢复；代价是视觉调用数量增加、需增加 Office 转页适配和持久检查点。

### B. 更换为可直接接收原文档的 API

可能简化部分文档接入，但增加另一套供应商配置、格式限制、费用及来源定位适配，不能保证直接消除大文件限制。用户未选此方案。

### 开源组件的使用决定（实施建议）

1. PDF 渲染直接复用仓库已有的 [pypdfium2](https://github.com/pypdfium2-team/pypdfium2)，按页打开/释放图像；不新增另一套 PDF 语义解析器。其自身为 Apache-2.0 / BSD-3-Clause，发行二进制时保留 PDFium 及所含依赖的许可。
2. 本机 Office 转页优先通过隔离子进程使用现有 Word/PowerPoint。提供 LibreOffice 命令适配；[Gotenberg](https://github.com/gotenberg/gotenberg) 的 LibreOffice 转 PDF 接口作为可选部署适配，明确配置后使用，不把 Docker 变成默认启动前提。Gotenberg 项目为 MIT，随附转换器许可另计。
3. 参考 [olmOCR](https://github.com/allenai/olmocr)（Apache-2.0）的逐页请求、并发上限和失败退避；参考 [Docling 的远程 VLM 路线](https://github.com/docling-project/docling/blob/main/docs/usage/vision_models.md)（项目 MIT）的页面视觉转换方式。它们证明可复用的处理模式，但不整体引入其模型、服务端和文档存储体系。现阶段没有复制其源码；若实施时复制，记录具体来源版本并保留许可证及署名。

## 用户可见行为

- 笔记本上传入口、课程资料入口和图片/文档混合上传入口提供相同的处理方式选择：`标准处理`、`全程 AI`。默认仍为标准处理；同一次上传批次选定一种路线。
- 设置面板持久保存新上传的默认处理路线，首次默认为标准处理；切换只影响新上传，运行中和重试任务使用原路线。显式上传参数优先于设置默认值，历史持久记录默认仍为标准处理。
- 资料、任务及批次响应返回路线、当前阶段、总页数、已完成页数和可重试错误。刷新后从服务器恢复状态。
- 全程 AI 的阶段为：准备页面 → AI 读取 → AI 组织 → 生成笔记 → 更新知识树 → 分析知识联系。笔记可用与藤蔓分析完成分别展示；没有适合联系时显示已完成且没有新关系。
- 重试保持原路线；对已有失败资料提供“改用全程 AI”动作，创建新读取版本，保留旧版本。已成功生成的资料切换路线不会自动追加第二份正文，须显式发起重新生成。
- 预检报告当前模型与转页能力。缺少视觉模型或 Office 转换器时给出具体原因与可用格式，不将扫描页空文本当作成功。

## 新路线的执行流程

### 1. 接收、冻结路线与准备页面

上传流式落盘、检查真实文件格式和归属；全程 AI 不执行用于提取正文/章节的本地解析器。PDF 只检查文件结构、权限和页数；Office 文件只检查容器后交给转换器，不能先用当前 DOCX 的 500 段落规则挡住新路线。

每次请求持久保存 `processing_route=standard|llm`。Material、图片任务及 NotebookGenerationInput 保持一致；ParseRun 和生成任务快照保存路线、模型名、非敏感 endpoint 标识、提示词和配置版本，绝不保存 API 密钥。复用成功解析时必须比较路线和配置身份，不能因 Asset 相同复用另一条路线的结果。

原格式与转页定位：PDF 保留原页码；PPTX 转 PDF 时保证一张幻灯片对应一页；DOCX 的页码标明“转换预览第 N 页”，同时保留原文件入口，不声称是原 Word 文档的固定页码。图片作为单页输入。

PDFium 按页渲染并及时释放资源，不把整份页面图片加载进内存。Office 转换在独立进程中有超时、专用临时目录及输出校验；关闭宏和外部链接更新，不操作用户已打开的文档或退出用户已有的 Office 进程。转换失败保留原件并终止该次读取。

### 2. 模型读取与证据保存

按页调用视觉模型，返回受约束的 JSON：页面状态、按阅读顺序的标题/段落/列表/表格/公式/图示说明，以及不确定内容。页面身份和来源 ID 由程序分配，模型不能指定任意 Asset、笔记或页码。

视觉 API 复用主模型连接配置；不要求另填 `NOTEBOOK_VISION_*`。扩展主客户端以支持图片内容、完整性检查、用量记录和可控错误，不改变旧文本调用行为。检测输出截断，必要时采用有限的页面分区/修复重试；失败页不能悄悄省略。

保留页面图像作为真实证据。模型生成的文字与解释标记为 `vision` 和模型识别；不伪造 bbox。全部页面均得到有效结果（包括模型明确判断为空白的页面）后，才形成可生成正文的当前 IR。未完成或失败页面保留在检查点中，旧的成功当前版本保持可读。

### 3. 模型组织笔记与知识树层级

新路线不调用现有基于标题匹配的语义规划器。模型先从每批识别结果提炼知识单元，再分层汇总为整份资料的章节结构，引用原文块 ID，判断与现有 Notebook 目录的补充关系。程序只校验引用范围、层级、数量上限和覆盖情况。

长资料通过分层汇总控制每个请求大小；每个源块须标记为已使用、仅证据或明确无需写入并给出理由，不能截取前若干页后报告整份完成。过大的单元继续按已识别块拆分，不截断正文。模型输出的标题层级随笔记正文写入现有小节索引，知识树据此显示；不另建独立树数据源。

笔记正文沿用现有结构化节点及 source map 契约，按计划分批调用主模型。将已校验批次结果存为持久检查点；全部批次完成后通过原有修订号检查和追加式写入提交正文。程序保留用户已编辑/锁定正文及来源约束；若生成时现有正文改变且影响计划，重新规划并使依赖旧计划的检查点失效，不盲目拼接过时计划。

### 4. 模型生成藤蔓关系

笔记写入后更新派生树索引并登记关系任务。标准路线的候选机制保持兼容；全程 AI 路线通过模型对所有有效跨课程小节的分批摘要进行筛选，再对选中两端的正文证据判断联系，不复用标题词重合的前 24 个候选截断。分层摘要也由模型产生，绑定小节版本。

关系筛选与判断均可分批恢复，记录已遍历的小节集合；不承诺模型会找到所有潜在关系。模型只可引用服务端给定的小节 ID，输出类型和具体依据。沿用现有归属、删除、隐藏关系、人工关系、版本指纹和过期检查。空关系是有效结果。关系阶段失败不回滚已经生成的笔记，并允许单独重试。

## 大文件限制与恢复

以下为实施建议值，并非用户另行指定：新路线默认上限 200 MiB、2,000 页，标准路线继续沿用现有配置；服务端能力接口分别返回每条路线的限制。限额可配置，超限时在模型调用前明确拒绝。

视觉读取默认每次一页、并发 2；请求按图片实际大小及服务商限制控制，必要时缩放或分区。规划与正文请求按独立预算分批。成本随完整读取页数增加；UI 展示页数、进度和取消入口，有价格配置时展示估算，否则仅显示用量，不编造费用。

增加持久步骤/批次表，记录所属读取或生成/关系任务、阶段、批次键、输入指纹、状态、尝试次数、校验后的 JSON 结果、用量及错误。唯一键包含任务身份、阶段和批次；输入指纹包含文件哈希/页面、路线、模型、提示词及相关正文版本。只有完全匹配的成功批次可复用。

网络超时、429、5xx 采用有上限的退避（含 Retry-After）；认证、额度或模型不支持图片时停止并给出明确错误。工作执行器在阶段/批次间可让出调度，长资料不能长期阻塞其他课程任务；提交结果前校验领取身份和 attempt。重启或手动重试从最后有效检查点继续。不能保证供应商在客户端断线时没有计费，必须避免把重试描述为绝对不重复收费。

取消在当前模型请求结束或超时后生效；已存检查点保留，未完成正文不写入。多路线同时给一个 Notebook 写入仍遵循现有串行生成约束。混合路线的待生成输入分别建任务，不能以同一生成快照覆盖两种策略。

## 接口与迁移范围

- 所有文档、图片上传端点接受相同的可选路线字段；旧调用缺省为 `standard`。批次中后续文件必须匹配首个文件的路线；不匹配返回可操作错误。
- 重试接口复用原路线；显式切换路线通过新的读取请求提交。重复上传、重复请求和同一 Asset 切换路线的幂等键包含路线/配置身份，避免错误复用或重复正文。
- capabilities、Material/Asset、ParseRun、任务和批次响应以及前端类型补充路线和阶段进度。错误结构保持兼容。前端两类上传页面及共享上传状态一起更新。
- 采用 Alembic 增加路线与检查点字段/表，旧记录回填为 `standard`；旧快照缺少路线时按标准处理。升级不删除业务数据，验证迁移与重启恢复。
- 本功能不改主 API 密钥、用户数据库路径或现有上传文件。验证使用隔离数据目录和合成文档；文档更新覆盖解析、API、数据契约与验收。

## 验证和交付边界

1. 双路线 API 和旧客户端兼容；故意让本地文字/OCR解析器抛错时，全程 AI 的 PDF、图片流程仍能读取并生成。
2. 合成 PDF、PPTX、DOCX、空白/扫描页、公式和表格验证转页与来源定位；Office 转换器不存在、失败和超时均有明确状态。
3. 超过旧限制的合成文档验证新路线准入、分批和恢复；结构化模型桩可验证 500 页以上的调度，真实 API 用少量合成页验证多模态请求与端到端质量。两类验证分别报告。
4. 批次中间失败、429、截断 JSON、取消、重启、重复请求、模型变更、正文并发编辑和软删除；已成功批次复用，旧数据和用户修改受保护。
5. 树来自模型生成的正文层级；藤蔓引用有效且当前的两端小节；无关系、单独失败重试及超过 24 个候选的小节遍历可验证。
6. 运行后端相关测试及完整检查、前端测试与构建；浏览器检查两种上传入口、选择、状态刷新和重试。外部 API、Windows Office 和大文件实际验证的范围、用时与限制单独记录。

## 留给实现者的常规选择

检查点表和模块命名、具体批次预算、模型 JSON schema、UI 控件样式、各转换器发现顺序及测试组织可由实现者在上述边界内决定。小预算与并发默认值以实际合成样例验证后调整。未授权提交、推送、合并或系统级安装；本设计文件可先留在工作区供确认。
